# 华为杯求解规范（阶段 3：求解计划 + 逐题求解）— 题面约束优先 / 模块化架构版

> 本文件用于【华为杯中国研究生数学建模竞赛】求解阶段。进入该阶段后，必须先 Read 本文件，再读取赛题正文、全部附件说明与数据文件。
>
> **核心原则**：题面硬约束优先于任何通用模板；先读懂题与附件，再定方法；先建立可验证的基线，再做改进；先算后画、计算与绘图彻底分离；所有论文结论必须能追溯到求解结果；官方要求提交的答案文件必须保持原格式、原结构、原文件名。
>
> 本规范以通用版 `求解规范模板.md` 为基础，保留现有 `求解规范.md` 的模块化、CSV 数据仓库和后期易改图思想，并针对华为杯赛题常见特点加强：**多格式附件、题面方法限制、CPU/运行时间约束、训练/测试集、指定答案表、时空大数据、机理模型、组合优化、鲁棒性、工程可解释性与 AI 使用留痕**。

## 零、规则优先级（★ 最高优先级）

执行时严格按以下优先级：

1. **赛题正文中的硬性要求**
2. **赛题附件说明、答案表说明、官方给定公式/参数/代码说明**
3. **本《求解规范.md》**
4. `求解计划.md`
5. 代码实现习惯

若冲突，永远服从更高优先级。

以下均视为**硬约束**，一旦题面出现必须逐条落实，不能被通用模板覆盖：

- “不得使用机器学习”“不建议使用机器学习”等方法限制
- CPU / GPU 限制
- 单次计算时间、实时性、复杂度要求
- 指定的评价指标、误差定义、置信水平
- 指定训练集 / 测试集及测试集不可见标签
- 指定样本必须在正文列出
- 指定答案表、指定列、指定数字编码、指定小数位数
- “保留原文件名并作为附件提交”
- 指定数据源引用方式
- 指定坐标系、时间尺度、单位、参考系
- 题目给定的物理规律、工程约束和边界条件
- AI 工具使用与披露要求

**禁止为了套模板而违反题面。**

## 一、整体求解流程

华为杯求解统一走以下主流程：

**环境检查与初始化 → 读题与附件清点 → 建立题面约束清单 → 数据/模态/提交格式审计 → 制定求解计划 → 基线模型 → 主模型 → 改进模型（如有必要）→ 独立验证与敏感性分析 → 生成结果数据 → 生成论文图 → 生成官方提交材料 → 最终一致性复核 → 交接论文阶段**

每个问题都尽量形成完整闭环：

**输入定义 → 数据处理 → 数学建模 → 算法求解 → 结果验证 → 对比分析 → 图表输出 → 结果留档**

但若题目本身属于纯理论推导、机理建模、仿真或建议型问题，不强制套数据建模流程。

规则：

1. **原始题目和原始附件只读，不覆盖。**
2. 每个问题至少有一个主入口脚本 `问题X.py`。
3. 同一问题计算复杂时允许拆成多个模块，但必须保留唯一主入口。
4. 共用函数放 `求解/公共/`，禁止跨问题复制多份同样代码后各自修改。
5. 若问题一预处理结果会被后续问题共享，则保存到 `数据/中间/` 或 `求解/预处理数据.csv`；若各题数据互不依赖，不强制问题一输出统一预处理文件。
6. 逐题求解完成后进入【阶段 4：写论文】，先 Read `论文/论文章节规范.md`。
7. 论文需要的数字、图、表必须能从 `求解/结果索引.md` 定位到来源。
8. `求解/`、`数据/` 是事实源；`提交附件/支撑材料/` 是由 `求解/支撑材料清单.json` 构建的可提交快照，不得在快照中单独手改代码、数据或图表。
9. 每问完成时同步构建并审计该问支撑材料；论文定稿后重建全包并完成 final 审计。未经审计不得把该问或全流程标记完成。

### 2.1 Python 项目虚拟环境规范（★ 自动初始化）

每个新的华为杯比赛项目必须在**项目根目录**建立独立 Python 虚拟环境，禁止直接依赖系统全局 Python 环境。Codex 进入求解阶段后，应先完成虚拟环境检测与初始化，再进行读题、数据审计和模型求解。

#### 2.1.1 自动检测与创建

进入项目后，先检查项目根目录是否存在：

```text
.venv/
```

若已存在，则直接复用，不重复创建。

若不存在，则自动执行：

```powershell
python -m venv .venv
```

Windows 下后续统一使用项目内解释器：

```text
.venv\Scripts\python.exe
```

以及通过该解释器调用 pip：

```text
.venv\Scripts\python.exe -m pip
```

**禁止假设终端中的 `python` 命令始终指向正确解释器。**  
虚拟环境创建完成后，后续数据处理、模型训练、优化、绘图和脚本执行均必须优先显式调用项目内 `.venv` 的 Python。

#### 2.1.2 创建后核验

创建或复用虚拟环境后必须执行：

```powershell
.venv\Scripts\python.exe -c "import sys; print(sys.executable)"
.venv\Scripts\python.exe --version
```

必须确认：

- `sys.executable` 指向当前比赛项目根目录下的 `.venv`；
- Python 可以正常启动；
- 不得在核验失败时静默退回系统全局 Python。

若核验失败，应先检查：

```powershell
python --version
python -c "import sys; print(sys.executable)"
```

确认本机 Python 安装与 `venv` 模块是否正常，再处理环境问题。

#### 2.1.3 基础依赖安装

虚拟环境首次创建后，只安装华为杯通用基础依赖：

```powershell
.venv\Scripts\python.exe -m pip install --upgrade pip
.venv\Scripts\python.exe -m pip install numpy pandas scipy matplotlib seaborn statsmodels scikit-learn openpyxl chardet networkx
```

基础依赖用途：

- `numpy`：数值计算；
- `pandas`：表格数据与结果处理；
- `scipy`：科学计算、插值、优化、信号处理、统计；
- `matplotlib`：核心科研绘图；
- `seaborn`：统计可视化；
- `statsmodels`：回归、统计模型、残差分析、Q-Q 图等；
- `scikit-learn`：传统机器学习、评价指标与数据处理；
- `openpyxl`：Excel 数据及官方答案表；
- `chardet`：文本编码识别；
- `networkx`：网络、DAG、调度关系等图结构。

不得因为“以后可能用到”而一次性安装大量大型依赖。

#### 2.1.5 requirements.txt

环境初始化完成后，在项目根目录生成：

```powershell
.venv\Scripts\python.exe -m pip freeze > requirements.txt
```

规则：

1. `requirements.txt` 用于记录该比赛项目**实际安装和使用**的 Python 依赖版本；
2. 后续新增依赖后重新生成；
3. `.venv/` 不作为竞赛提交内容，`requirements.txt` 保留用于复现；
4. 不允许手工删除实际依赖后仍保留失真的依赖清单。

#### 2.1.6 Python 脚本执行规则

后续所有 Python 脚本默认显式使用项目虚拟环境，例如：

```powershell
.venv\Scripts\python.exe 求解\问题一\问题一.py
```

而不是直接依赖：

```powershell
python 求解\问题一\问题一.py
```

这样保证 Codex、VS Code Terminal 与人工复现使用同一解释器和同一依赖环境。

如需在 Python 中调用其他 Python 子进程，也应优先使用：

```python
import sys
python_exe = sys.executable
```

不得重新硬编码系统 Python 路径。

#### 2.1.7 VS Code 解释器一致性

项目初始化后，应优先让 VS Code 使用：

```text
项目根目录\.venv\Scripts\python.exe
```

作为当前工作区 Python Interpreter。

若当前 VS Code Interpreter 与 `.venv` 不一致，不得据此修改模型代码来适配错误环境；应先统一解释器。

#### 2.1.8 异常处理

若虚拟环境创建或依赖安装失败：

1. 检查本机 Python 是否正常；
2. 检查 `venv` 是否可用；
3. 检查网络 / pip 源 / 权限；
4. 只定位并处理失败步骤或失败包；
5. 不反复删除整个环境重装；
6. 不静默退回全局 Python；
7. 若连续排查仍无法解决，应停止环境初始化并明确报告具体错误。

#### 2.1.9 提交与清理规则

`.venv/` 属于本机运行环境：

- 不写入论文；
- 不作为竞赛结果附件；
- 不复制进提交附件；
- 不依赖其中的绝对路径写论文或代码。

项目中保留：

- `requirements.txt`
- 求解代码
- 必要配置文件
- `求解/环境与依赖.md`

`求解/环境与依赖.md` 应记录：

- Python 版本；
- `.venv` 是否创建成功；
- 当前解释器路径；
- 实际使用的关键 Python 包；
- R / `Rscript` 是否可调用；
- TeX Live / `xelatex` 是否可调用；
- 赛题专用额外依赖。

### 2.2 本项目统一工具链：Python + R + TeX Live

华为杯项目默认只使用以下三类可由 Codex 通过代码或命令行自动执行的工具：

1. **Python**：默认主力，负责数据处理、科学计算、优化、机器学习/深度学习、图像处理、信号处理、网络与几何计算以及绝大多数科研绘图；
2. **R**：统计分析与统计科研绘图的补充工具，仅在 R 对当前任务有明显表达或实现优势时使用；
3. **TeX Live**：负责 XeLaTeX 论文编译以及 PGF/TikZ 矢量流程图、模型框架图和结构示意图。

默认不引入 MATLAB、Origin、Graphviz 等额外软件。若未来赛题明确提供只能依赖特定软件的官方程序或格式，再单独评估，不得仅为了“图更高级”增加大型软件环境。

项目初始化阶段必须检查：

```powershell
Rscript --version
xelatex --version
kpsewhich tikz.sty
```

若 R 不可用，则统计分析与绘图自动退回 Python；若 TikZ 不可用，则先修复 TeX Live/PGF 环境，不得用截图代替论文结构图。

**工具选择优先级：**

```text
能用 Python 高质量完成 → Python
R 在统计建模/统计图上明显更简洁或更成熟 → R
流程图/模型结构图/论文排版 → TeX Live + TikZ
```

同一分析任务原则上保持单一工具链，避免为了展示软件数量而频繁在 Python 与 R 之间切换。

### 2.3 支撑材料机器协议与生命周期（★ 强制）

确定问题数量后，立即初始化：

```powershell
.venv\Scripts\python.exe 华为杯_求解规范/tools/init_supporting_materials.py --output 求解/支撑材料清单.json --project-title "赛题题目" --question q1:问题一 --question q2:问题二
```

清单的结构以 `华为杯_求解规范/支撑材料清单.schema.json` 为准。每问至少登记：

- 唯一主入口、原项目运行命令；
- 本问完整运行所需的全部自编源码和共享模块，而不只是一段核心代码；
- 实际运行命令、`pass/fail`、核验时间和非空运行记录；
- 正文因篇幅未完整展示、但对复核有价值的较大篇幅中间图与表；若没有，也必须写明审查结论，不能留空或保留“待审查”。

自主查阅、整理或爬取的数据只指赛题官方原始数据之外、实际进入模型或结论的数据。必须保存到 `数据/自主/`，并登记本地数据文件、来源/URL 或可定位出处、获取日期、获取与整理方式、许可或使用条款、使用问题、采集/整理脚本（如有）和独立来源记录。赛题官方原始数据不得伪装成自主数据重复打包。

每问真实运行并完成结果图表后：

```powershell
.venv\Scripts\python.exe 华为杯_求解规范/tools/build_supporting_materials.py --manifest 求解/支撑材料清单.json --project-root . --output 提交附件
.venv\Scripts\python.exe 华为杯_求解规范/tools/audit_supporting_materials.py --manifest 求解/支撑材料清单.json --stage question --question-id q1 --project-root . --output 提交附件 --report 求解/问题一/结果/支撑材料.audit.json
```

构建器会重建工具管理的 `提交附件/支撑材料/` 快照并刷新根目录 `readme.md`、机器构建清单和 SHA-256；不会删除或改写 `提交附件/最终提交文件/`。上游源码、外部数据、图表或核验记录变化后必须重新构建，禁止保留漂移的旧副本。

## 五、数据与附件审计

### 5.1 先 Read，再写代码

任何数据文件第一次使用前，先输出：

- shape / 尺寸
- 字段名 / 变量名
- dtype
- 缺失值数
- 重复值数
- 异常值范围
- 唯一类别
- 单位
- 时间范围
- 空间范围
- 是否存在嵌套数组、字符串数组或变长字段

禁止猜列名、猜单位、猜标签编码。

### 5.2 常见华为杯文件格式处理

#### CSV

- 优先 `pandas.read_csv`
- 自动检测 UTF-8 / GBK / UTF-8-SIG
- 对字符串形式的数组、列表字段先解析，再统计
- 不允许默默丢弃解析失败的行

#### XLSX / XLS

- `.xlsx`：优先 `openpyxl` / `pandas`
- `.xls`：使用兼容引擎读取
- 读取时保留 Sheet 名、原行号、样本编号
- 官方答案表必须先复制到 `提交附件/原始模板备份/`

#### MAT

- 普通 MAT：`scipy.io.loadmat`
- v7.3/HDF5：`h5py`
- 加载后打印变量名、维度、轴含义
- 若时间轴与风机/样本轴容易混淆，必须先人工逻辑核验

#### TXT

- 先检查编码、分隔符、注释行、单位
- 科学计数法与高精度参数不得因默认格式丢精度

#### DOCX / PDF

- 用于读取赛题、附件说明、公式、方法限制
- 不把说明文档中的示例结果当作本题计算结果
- 若题面给出公式，先记录变量定义与单位，再实现

#### GeoTIFF

- 记录 CRS、transform、resolution、nodata、extent
- 统一空间分析前必须检查投影与分辨率
- 面积统计时必须考虑地理坐标下像元面积并非常数

#### NetCDF

- 使用 `xarray` / `netCDF4`
- 检查维度名称、时间编码、经纬度方向、缺失值
- 大文件优先切片、懒加载、分块，不一次性全部转 DataFrame

#### BSP / 星历文件

- 优先使用赛题提供的读取示例和可靠天文库
- 明确时间尺度、参考系、历元、单位
- 高精度时间与坐标不得用低精度字符串或 float 截断

### 5.3 原始数据不可变

禁止：

- 在原附件上直接清洗
- 覆盖训练集/测试集
- 手工改动测试样本
- 删除不符合预期的数据而不留记录

清洗后的数据写入：

`数据/中间/`

赛题官方原始数据之外、自主查阅/整理/爬取且实际用于建模的数据写入 `数据/自主/`；同步保存来源记录和采集/整理脚本，并登记到 `求解/支撑材料清单.json`。仅用于阅读理解、未进入模型的数据仍应在论文引用或调研记录中说明，但不冒充模型输入。

### 5.4 ZIP / RAR / 嵌套压缩包审计

华为杯附件可能包含多层 ZIP、RAR 或大规模数据包。**禁止收到压缩包后直接全部解压再盲目读取。**

先执行：

1. 列出压缩包目录结构；
2. 统计文件数量、压缩后大小、预计解压大小；
3. 识别内部文件类型与嵌套压缩包；
4. 判断哪些文件真正对应当前问题；
5. 仅将需要处理的文件解压到工作目录，原压缩包保持只读。

若附件文件名存在编码异常，只允许在**工作副本**中规范化文件名，并保存：

`数据/文件名映射.csv`

记录“原文件名 → 工作文件名”，不得修改官方原附件。

对于数百 MB 或更大的数据集，优先采用按文件、按批次、按变量读取，不为了方便将全部内容一次性展开成巨型 DataFrame。

### 5.5 图像 / 像素数据审计

首次读取 JPG / PNG / TIFF / WEBP 等图像时，必须记录：

- 原始文件名；
- 宽 × 高像素；
- 通道数与色彩空间；
- 数据类型 / 位深；
- DPI（若存在）；
- EXIF 方向（若存在）；
- 图像对应的实际物理尺寸与单位（若题面给出）；
- 像素坐标与物理坐标的映射关系。

原图只读。任何裁剪、缩放、旋转、去噪、增强、二值化都输出到工作目录，并记录变换参数。

**若题目要求输出结果与原图像素尺寸完全一致，则最终保存前必须用代码 assert 宽度、高度完全相同。**

若需要把像素结果映射回 mm、m、角度、深度等物理坐标，必须建立显式转换函数，不得直接把像素距离当作物理距离。

### 5.6 矢量图 / CAD / 多模态附件

若赛题同时提供 DWG、PDF 矢量图、坐标 XLSX、JPG 平面图等多种等价或互补资料：

1. 优先使用官方同时提供的、当前工具链可稳定读取的开放或导出格式；
2. 若 DWG 同时有官方 PDF/XLSX 等等价信息，**不为了读取 DWG 安装 CAD 软件**；
3. PDF 若需读取矢量路径、页面坐标或高分辨率渲染，可按需使用 Python 的 PyMuPDF 等库；
4. 表格坐标、平面图像、矢量边界之间必须统一原点、方向、比例尺和单位；
5. 多模态信息融合前，先验证不同来源是否指向同一空间对象和同一坐标参考；
6. 照片、视频等示例资料若题面明确说明仅供参考，不得将文件名、拍摄季节、视角等未被题面支持的信息过度解释为标签或重要性。

## 七、方法选择总则：题面约束 > 模型复杂度

**禁止固定“所有机器学习只能某框架”这种一刀切策略。**

华为杯赛题跨度很大，方法必须按题目选择。

### 7.1 方法选择顺序

优先级：

1. **题面直接给出的机理、公式、约束**
2. 可解释的经典数学模型
3. 统计 / 回归 / 优化方法
4. 机器学习
5. 深度学习
6. 复杂集成或自定义算法

能用简单模型高质量解决，不为了“高级”强行上深度学习。

### 7.2 基线—主模型—改进模型

每个核心问题尽量建立：

- **Baseline**：简单、可解释、能快速跑通
- **Main Model**：最终主方法
- **Improved Model**：只有在基线/主模型存在明确不足时再加入

论文中的“创新”优先来自：

- 题意抽象
- 约束构造
- 特征设计
- 机理修正
- 多目标权衡
- 鲁棒处理
- 复杂度降低
- 验证设计

不是单纯把模型名字变复杂。

### 7.3 证据链式内容扩展（Evidence-chain Expansion）

默认不把“建模 → 得到一个结果 → 放一张表”当作完整答复。每个核心问题求解后，围绕一个可复算的核心结论，按实际适配性建立：

```text
问题定义 → Baseline/参考方案 → 主模型 → 求解 → 核心结果
→ 独立验证 → 对比分析 → 敏感性/稳定性/鲁棒性
→ 题意或机理解释 → 本问结论
```

这是一条可裁剪的证据链，不是每问都必须穷举所有环节，更不是为页数增加无关内容。`求解/求解计划.md` 中每问必须新增“证据矩阵 / Evidence Matrix”，并同步写入 `求解/视觉计划.json`。每行除“适用、无需、不可做及原因”外，还必须填写数据形态、`figure / schematic / table / text / N/A` 表达方式、所需结构化结果路径和关联 Figure/Schematic ID。至少逐项审查：

- 核心结论、Baseline 和主模型；
- 可独立实现的第二路径、解析量、守恒量、参考值或理论边界；
- 误差/约束指标、分组误差、极端样本和误差口径；
- 值得扫描的参数或输入，以及可移除的模型组件；
- 随机种子、噪声、缺失、延迟或环境扰动是否构成真实鲁棒性问题；
- 场景、规模、权重、约束强度、运行时间或收敛是否需要报告；
- 是否存在容易混淆的单位、符号、坐标、时间尺度或约束定义，因而需要“正向支持 + 反证排除”；
- 可组合为同一科学问题下多面板 Figure 的结果。

凡是多点扫描、重复试验、分布、误差结构、矩阵/响应面或空间几何，默认优先使用 Figure；改用表格或文字必须解释为什么图形不能增加可验证信息。主结果必须有 Figure；标准或复杂问题的独立验证也必须有 Figure。Figure Plan 第一版必须早于本问代码实现，并反向声明 CSV/JSON 字段、扫描范围、重复次数、统计量和单位。

篇幅规划同时参考模型复杂度、证据矩阵丰富度、真实结果数量和问题重要程度，绝不按问题数量平均分配。每一个新增 Figure、Table 或小节都必须回答一个新的分析问题；重复呈现同一数值不是证据扩展。

### 7.4 题型的可选证据模块

按题型从以下候选中选择真实适用模块：

- 回归、时序、预测：朴素/季节朴素基线，有意义的 1--3 个竞争模型，MAE/RMSE，预测--真值、残差/覆盖率、分组误差、外推、特征贡献或消融；
- 分类：多数类或简单模型基线，Accuracy/Macro-F1/Precision/Recall，混淆矩阵、ROC/PR（适合时）、类别误差、阈值、特征贡献、种子稳定性；
- 机理模型：定律与推导、量纲/数量级、参数来源、独立解析或数值路径、守恒、边界/极限、参考值、参数扰动和错误假设反证；
- 优化、调度、组合优化：无优化/简单启发式基线、可行性与官方指标独立复算、优化前后、权重或约束扫描、Pareto、收敛、多初值、规模--时间和最优性 Gap（可获得时）；
- 多目标优化：单目标极值、加权和基线、Pareto 前沿、代表折中点、目标冲突、权重或 $\epsilon$ 扫描、场景下前沿移动；
- 仿真、随机过程：理论与模拟分布、独立采样、Monte Carlo、均值/方差收敛、种子与样本规模敏感性、理论上下界；
- 图论、DAG、空间或图像任务：简单可行方案、独立验证器、约束违例/几何或结构一致性、不同规模/结构/场景、时间和内存；
- 鲁棒与不确定性：无扰动/无鲁棒基线、不同噪声/缺失/延迟/参数扰动、退化曲线、最坏情形和置信区间。

候选模型比较只在选型、改进或适用边界确有意义时进行。通常“一个简单 Baseline + 一个主模型 + 一至两个有意义竞争方案”已足够；禁止为凑页数训练大量不适用模型。

### 7.5 题面禁止机器学习时

若写明“不得使用机器学习”：

- 不得使用随机森林、XGBoost、神经网络、Boosting 等
- 不得用机器学习模型偷偷做中间预测再包装成解析法
- 可使用数值优化、统计估计、信号处理、解析推导、迭代算法

### 7.6 题面“不建议机器学习”时

默认先使用：

- 机理
- 回归
- 最小二乘
- 参数辨识
- 插值
- 小样本统计方法

只有能够证明数据规模、验证结果和可解释性足够，才考虑机器学习。

### 7.7 机器学习框架

- 传统机器学习：优先 scikit-learn
- 梯度提升：按需 XGBoost / LightGBM
- 神经网络：优先 PyTorch
- 不使用 TensorFlow / Keras / JAX，除非赛题附件或既有代码明确依赖
- 所有随机模型固定随机种子

## 八、不同问题类型的建模要求

### 8.1 描述统计 / 因素分析

至少回答：

- 分布是什么
- 时间如何变化
- 空间如何变化
- 类别间有何差异
- 单因素影响有多大
- 交互作用是否存在
- 结论是否稳健

不允许只画图不量化。

常用方法：

- 均值 / 中位数 / 分位数 / CV
- 趋势斜率
- 变化率
- 方差分解
- ANOVA / 非参数检验
- 相关 / 偏相关
- 双因素交互项
- 效应量

### 8.2 分类问题

必须包含：

- 类别分布
- 特征构造依据
- 训练/验证划分
- 混淆矩阵
- Accuracy / Macro-F1 等适合指标
- 类别不平衡处理说明
- 误分类样本分析
- 测试集最终预测

若测试集无标签：

- 不在测试集上计算“准确率”
- 不用测试集预测结果反向调模型
- 参数只由训练/验证决定

### 8.3 回归 / 预测问题

必须至少给出：

- 基线模型
- 主模型
- MAE / RMSE / R² 或题面指定指标
- 残差分析
- 极端值误差
- 泛化验证

若数据具有时间结构：

- 禁止普通随机切分造成未来信息泄漏
- 使用按时间划分或 rolling validation

若数据具有空间结构：

- 禁止相邻像元随机切分造成空间泄漏
- 优先分区 / block / region holdout

### 8.4 机理模型 / 参数辨识

必须写清：

- 基本定律
- 假设
- 变量
- 单位
- 方程
- 参数
- 参数来源
- 数值求解方法
- 边界条件 / 初始条件
- 与参考值或极限情况的验证

### 8.5 优化问题

必须明确三要素：

1. 决策变量
2. 目标函数
3. 约束条件

如果多目标：

- 明确每个子目标量纲
- 说明归一化方式
- 说明权重来源
- 做权重敏感性分析
- 或使用 Pareto 前沿，不要随意拍权重

求解后必须验证：

- 所有硬约束满足
- 等式约束误差
- 不等式最大违反量
- 目标改进幅度
- 与 baseline 对比
- 运行时间
- 多次随机初始化稳定性（若适用）

### 8.6 鲁棒 / 不确定性问题

必须先区分：

- 测量噪声
- 缺失
- 延迟
- 随机扰动
- 参数不确定性
- 分布漂移

至少设计：

- 无鲁棒处理 baseline
- 鲁棒方法
- 不同扰动强度对比
- 性能下降曲线
- 最坏情况或置信区间

### 8.7 图像分割 / 像素识别 / 计算机视觉问题

当题目要求识别裂纹、缺陷、目标区域、语义类别或输出二值图时，必须把问题明确区分为：

- 图像分类；
- 目标检测；
- 语义/实例分割；
- 传统图像处理与几何提取。

不得把“像素级识别”误做成仅给整张图片分类。

**基本流程：**

```text
图像审计
→ 干扰类型分析
→ baseline
→ 主方法
→ 后处理
→ 几何/连通域提取
→ 输出尺寸与编码核验
→ 定量/结构验证
```

Baseline 优先考虑可解释的传统方法，例如灰度/颜色变换、滤波、边缘、阈值、形态学、连通域、Hough/RANSAC、区域生长等；只有在数据量、标签条件和任务收益支持时再使用深度学习。

按需 Python 包：

- `opencv-python`
- `scikit-image`
- `Pillow`
- `torch`
- `torchvision`

若无人工真值标签，不得虚构 IoU、Dice、Pixel Accuracy 等监督指标；应改用人工抽查子集、几何一致性、连续性、重复性、拟合残差、工程规则一致性等可验证证据。

若题目要求黑白二值图，必须明确：

- 前景/目标像素取值；
- 背景像素取值；
- 图像模式；
- 输出宽高；
- 文件格式。

### 8.8 振动 / 时序信号处理与跨域迁移问题

对于振动、声学、电流等连续采样信号，首先根据机理判断时域、频域、包络谱、时频域中哪些特征具有物理意义，不得只把原始序列丢入模型。

按需分析：

- 均值、RMS、方差、峰值、峰峰值；
- 偏度、峭度、波形指标、脉冲指标、裕度指标；
- FFT / 功率谱；
- 包络解调；
- STFT；
- 小波 / 小波包；
- 故障特征频率及其倍频、边带；
- 转速/工况相关特征。

按需 Python 包：

- `scipy.signal`
- `PyWavelets`
- `torch`
- `torchvision`

**窗口切分防泄漏铁律：**

若一个原始文件会被切成多个窗口，必须先按“原始文件 / 设备 / 工况”划分 train/val/test，再在各集合内部切窗。禁止先把同一条长信号切成大量窗口后随机分到训练集和测试集，否则会造成严重的数据泄漏。

**采样率 / 转速 / 工况对齐：**

不同域或不同文件存在采样率、转速、传感器位置差异时，必须先分析是否需要：

- 抗混叠滤波；
- 重采样；
- 阶次归一化；
- 频率轴归一化；
- 传感器通道筛选；
- 幅值标准化。

不得直接把不同采样率数据按相同数组索引比较。

**无标签目标域：**

若目标域标签未知：

- 参数、阈值、迁移强度不能依据目标域真实标签调优；
- 不得报告目标域 Accuracy/F1，除非官方后来提供标签；
- 应采用适用于无标签目标域的迁移/域适配方法；
- 目标域预测标签属于模型输出，不等同于“已验证真值”。

迁移效果可通过源域泛化、特征空间分布、MMD/域差异、聚类结构、物理特征一致性和可解释性等辅助证据分析。

### 8.9 图论 / DAG / 调度 / 缓存分配类组合优化

对于计算图、任务调度、缓存分配、路径依赖等问题，**独立验证器必须先于复杂优化器建立**。

至少分别实现：

1. 输入解析器；
2. 可行性验证器；
3. 官方指标计算器；
4. baseline；
5. 主优化算法；
6. 提交文件生成器。

验证器不得复用主算法内部“自认为正确”的状态，而应尽可能根据原始输入和最终输出独立重算。

图调度类至少检查：

- 每个节点是否恰好出现一次；
- 拓扑依赖是否全部满足；
- 新增节点及依赖是否符合题面规则；
- 缓存地址是否越界；
- 生命周期重叠时地址是否冲突；
- SPILL 操作是否完整；
- 资源/执行单元独占约束；
- 官方定义的执行时间；
- 官方定义的数据搬运量。

大规模图优先使用邻接表、稀疏结构、增量更新，避免不必要的全传递闭包和 O(N³) 计算。

若官方要求多个示例计算图的结果必须出现在正文，`求解计划.md` 和 `结果索引.md` 中必须建立“正文必报结果清单”，不能只生成附件。

### 8.10 路径规划 / 平面几何 / 空间布局问题

当问题涉及园路、建筑边界、水体、植物、区域分区、视域或空间布局时，应先把几何数据转换成明确的数学对象：

- 点；
- 折线；
- 多边形；
- 图节点/边；
- 邻接关系；
- 可通行域/不可通行域。

按需 Python 包：

- `shapely`
- `networkx`
- `scipy.spatial`
- `opencv-python`

路径规划必须明确：

- 起点/终点；
- 节点定义；
- 边生成规则；
- 路径长度；
- 转折；
- 交叉/分岔；
- 重复边或重复区域惩罚；
- 目标函数；
- 可行性约束。

空间“开阔/围合”“异景程度”“复杂性”等主观概念必须先转化为可计算指标，再做标准化、权重或综合评分；不能直接凭视觉感受给分。

### 8.11 三维几何重构 / 连通网络问题

若题目要求由多个二维截面、展开图、钻孔、传感器轨迹等恢复三维结构，应明确：

1. 各局部坐标系；
2. 向全局三维坐标的转换；
3. 几何对象表示方式（平面、曲面、线、点云、网格等）；
4. 不同观测对象的匹配/连通准则；
5. 连通概率或相似度模型；
6. 不确定性来源；
7. 三维结果的定量验证与可视化。

按需 Python 包：

- `numpy`
- `scipy.spatial`
- `scikit-image`
- `trimesh`
- `open3d`
- `pyvista`

只有第三维具有真实物理含义时才使用三维图。三维重构结果不能只给“好看的 3D 图”，必须同步输出可核验的几何参数、连通关系或不确定性指标。

补充测点/钻孔/传感器位置优化应建立明确的价值函数，例如信息增益、不确定性降低、覆盖率提升或连通判别能力提升，并在资源数量约束下排序。

### 8.12 多模态数据融合与外部资料

当同一问题同时使用：

- 表格；
- 图像；
- 矢量图；
- 视频；
- 文本说明；
- 网络资料；

必须先建立“模态—用途—坐标/样本对应关系”，禁止简单把所有模态特征拼接后就称为多模态建模。

外部网络资料只有在题面允许时使用。使用时记录：

- 来源名称；
- URL；
- 获取日期；
- 用于哪个变量/样本；
- 是否经过人工校验；
- 本地保存文件名。

凡外部资料实际转化为模型数据、参数表、标签、边界条件或场景输入，还必须写入 `求解/支撑材料清单.json` 的 `external_data`，保存到 `数据/自主/`，并随最终支撑材料打包。不得只在正文给 URL 而不保留实际使用的数据版本和整理过程。

若外部资料只用于辅助理解，不应将其未经验证的主观描述直接作为模型标签。

## 九、验证规范（★ 华为杯高分关键）

验证不能机械地“所有题都 5 折交叉验证”。

根据数据结构选择：

- i.i.d. 表格数据 → K-fold / Stratified K-fold
- 时间序列 → chronological split / rolling validation
- 空间数据 → spatial block CV / region holdout
- 多设备 / 多站点 → GroupKFold
- 小样本机理问题 → 参考值对比 + 参数扰动 + 极限情况
- 优化问题 → 可行性验证 + baseline + 多初值稳定性
- 仿真问题 → 理论分布 / 守恒量 / 已知解析解 / Monte Carlo

### 9.1 禁止数据泄漏

以下操作必须只在训练集上 fit：

- 标准化
- PCA
- 特征选择
- 缺失值统计
- 类别编码的统计量
- 目标编码
- 超参数搜索

测试集只用于最终预测。

### 9.2 误差记录

保存：

`结果/模型误差汇总.csv`

建议包含：

- 数据划分
- 模型
- 参数
- MAE
- RMSE
- R²
- Accuracy
- Macro-F1
- 题面指定指标
- 运行时间
- 随机种子

仅保留与当前问题相关的指标，不强求全部填写。

### 9.3 结果稳定性

对随机算法至少：

- 固定 seed
- 记录 seed
- 必要时多次运行
- 输出均值 ± 标准差

若单次运行成本极高，至少说明随机性来源与固定策略。

### 9.4 独立评价器 / 官方规则复算（★ 强制用于有明确评分公式的题）

只要题目给出明确的：

- 可行性规则；
- 评分函数；
- 运行时间公式；
- 数据搬运量公式；
- 几何拟合指标；
- 输出编码要求；

就必须实现与主求解器分离的 `验证/评价` 函数或脚本。

推荐结构：

```text
主算法输出候选解
        ↓
独立验证器读取“原始输入 + 最终输出”
        ↓
重新检查所有硬约束
        ↓
独立复算官方指标
        ↓
生成验证报告.csv
```

论文中报告的关键指标优先来自独立评价器，而不是主算法训练日志中的临时值。

若主算法与独立评价器计算结果不一致，以独立评价器发现的问题为准，先修复再提交。

## 十、运行时间与复杂度

如果题面有实时性或 CPU 时间要求，**运行时间本身就是模型结果的一部分**。

### 10.1 计时要求

使用：

```python
from time import perf_counter

t0 = perf_counter()
result = solve(...)
elapsed = perf_counter() - t0
```

必须记录：

- CPU / GPU
- 是否包含数据读取
- 是否包含模型训练
- 是否仅统计单次在线推理 / 在线优化
- 重复次数
- 平均时间
- 最大时间

题面要求 `< 1 s` 时，不能只报告一次“碰巧小于1秒”的结果。

### 10.2 复杂度

对于算法设计题必须说明：

- 时间复杂度
- 空间复杂度
- 随数据规模增长的瓶颈

如理论复杂度不易严格给出，至少做：

- N 与运行时间曲线
- 数据规模与内存曲线

### 10.3 性能优化顺序

优先：

1. 算法层面降复杂度
2. NumPy 向量化
3. 减少重复 IO
4. 缓存中间结果
5. 稀疏矩阵
6. 分块
7. 并行
8. Numba / 编译优化

不能用“换更强硬件”掩盖算法不满足题面实时性。

## 十三、代码架构（★ 模块化）

总体原则：

**主函数 + 功能子函数 + 先算后画 + 一张图一个绘图函数**

### 13.1 推荐结构

```python
# 问题X.py

def 读取数据():
    ...

def 数据审计(df):
    ...

def 预处理(df):
    ...

def 构造特征(df):
    ...

def 基线模型(data):
    ...

def 主模型(data):
    ...

def 改进模型(data):
    ...

def 验证模型(result):
    ...

def 敏感性分析(result):
    ...

def 导出官方答案(result):
    ...

def main():
    raw = 读取数据()
    数据审计(raw)
    data = 预处理(raw)
    feat = 构造特征(data)
    base = 基线模型(feat)
    main_result = 主模型(feat)
    验证模型(main_result)
    敏感性分析(main_result)
    导出官方答案(main_result)

if __name__ == '__main__':
    main()
```

绘图放：

```python
def 绘制图1():
    df = pd.read_csv(...)
    ...

def 绘制图2():
    df = pd.read_csv(...)
    ...
```

### 13.2 计算与绘图彻底分离

计算函数：

- 读原始数据
- 预处理
- 建模
- 求解
- 验证
- 保存结果

绘图函数：

- **只读取已有结果**
- 不重新训练
- 不重新优化
- 不重新仿真

### 13.3 一张图 = 一个函数

后期改图时：

```text
改配色 → 只跑对应绘图函数
改图例 → 只跑对应绘图函数
改坐标轴 → 只跑对应绘图函数
```

不得因为改图重新跑数小时模型。

### 13.4 图很多时拆文件

```text
问题X/
├── 问题X.py
├── 模型_问题X.py
├── 绘图_问题X.py
├── 结果/
└── 图片/
```

每个问题在 `求解/求解计划.md` 中建立按题型裁剪的 Evidence Matrix 和 Figure Plan，并把同一字段写入 `求解/视觉计划.json`。Markdown 负责解释，JSON 负责自动门禁；ID、数据源、输出、标签和状态不得漂移。每个 Figure 至少记录：

- Figure ID、所属问题、核心科学问题和拟支撑结论；
- 真实数据源、结果文件、字段、生成脚本/函数和结果索引位置；
- 图型、Panel 数量与含义、布局、输出路径和论文标签；
- 视觉 token、线型、marker、单位、共享轴/色标，以及三维、渐变、透明度、柱状图或饼图的使用理由；
- `Figure archetype`、是否调用 `academic-figure-skill`、匹配的 `assets/figures/` 目录、`native run / visual adapt / cross-type inherit` 模式、Python/R 运行时、输出脚本、PDF/SVG/PNG/统计/QA 路径；
- 质量检查状态和不适用时的二维/多面板替代方案。

简单问题通常至少规划 2 个 Figure，标准或复杂问题通常 3--6 个；每个问题至少有主结果 Figure，标准或复杂问题还必须有独立验证 Figure。低于审查阈值时，必须逐项说明四类视觉证据为什么不适用以及用什么可复核证据替代。一个 Figure 可包含多个共同回答同一科学问题的 Panel；不得为了页数或数量机械补图。四问型标准/复杂赛题的组合级规划通常为 15--25 个非冗余 Figure，这只是审查带，不是图数硬目标。

Figure Plan 还要承担正文证据架构，而不只是绘图清单。对每个标准/复杂问题，逐项评估并定位：模型/机理或算法结构、主结果、候选比较/消融、独立验证、误差结构、参数/输入敏感性、鲁棒/场景与理论/失效边界。适用项应在求解阶段生成结构化结果并优先写回本问题章节；不适用项记录原因。全量逐折指标、特征字典、行数/允许值检查、序列化、哈希和支撑材料构建记录不是独立科学证据，不得据此规划正文大章。

页数和视觉密度在计划阶段前置审查：图表不能全部集中在论文前半段，也不能把后半段留给重复表格和交付说明。优先规划能够把真实高维结果压缩为可读证据的多面板 Figure，例如参数目标面+bootstrap、逐折误差森林图/热图、模型胜负结构、残差分层、设备/场景差异、特征响应和理论边界。每个 Panel 必须携带唯一证据；同一结果换颜色、换图型或拆成多个 Figure 不计为新增证据。

在任何求解代码编写前，先完成计划审计：

```powershell
python 华为杯_求解规范/tools/audit_visual_plan.py --plan 求解/视觉计划.json --stage plan --project-root . --report 求解/视觉计划.plan.audit.json
```

#### 16.1.1 Schematic Plan

轨道/空间几何、坐标变换、传播路径、物理作用关系、采样/分箱/折叠原理等不表达算法顺序的机理示意，建立 Schematic Plan；含输入—步骤—输出、迭代、反馈、验证门或决策分支的结构继续使用 Flowchart Plan。Schematic Plan 至少记录科学问题、真实题面/公式/代码/结果来源、元素及关系、TikZ 源、PDF/PNG、图题、label、正文引用和字体/灰度/版心/裁切状态。二者均走 TikZ/XeLaTeX；`academic-figure-skill` 的 `schematic_led` 只管理组合布局，不能替代真实性门禁。

#### 16.1.2 Flowchart Plan

只要题目具有多阶段模型、多问题依赖、数据—模型—输出—验证链条、分层模型结构或明确的迭代/反馈算法，Phase 2 必须先评估是否需要流程图、总体技术路线图、模型结构图或算法流程图。流程图不是必选装饰；若文字、公式和表格已经足以表达逻辑，应在计划中记录“不需要流程图”及理由。

“每问一个流程图”不是通用数量要求。若各问共享同一条数据流，应使用一张总体技术路线图，并只为具有独立循环、分支、优化或验证闭环的问题增加局部流程图；若问题的算法可以用短伪代码更准确表达，则优先伪代码。任何流程图都不得为补页重复总体路线。

确需流程图时，必须先完整读取 `华为杯_求解规范/华为杯_绘图规范.md`，根据真实模型结构建立 Flowchart Plan，完成节点/箭头真实性审查后才可生成。Flowchart Plan 至少记录：

- Flowchart ID、所属问题或全篇、流程图结构类型；
- 要解释的科学问题和拟支撑的结论；
- 输入节点、中间模型/算法节点、输出节点和验证节点；
- 每个节点的题面/数据/代码/公式/结果来源；
- 节点之间的真实依赖、箭头方向和箭头传递的信息；
- 是否存在循环、反馈、分支、分层、右侧验证区或底部总体汇总，以及其证据；
- 推荐布局、可选 BrightTech-Info 颜色语义和灰度辅助编码；
- TikZ 输出路径、语义化文件名、LaTeX 图题、唯一 label 和正文引用位置；
- 渲染、字体、节点重叠、箭头穿字、版心、裁切、灰度、缩放和结果索引状态。

结构类型只能从绘图规范定义的总体技术路线图、分层系统架构图、纵向算法流程图、双阶段/多阶段协同流程图、输入—模型—输出—验证图或数据流/模块关系图中按真实结构选择，不得固定为某种模板。A/B/C 代码只能作为论文规范中的历史示例，不能复制其节点、公式、颜色、字号、框数、布局或箭头文字。

Flowchart Plan 未完成、节点/箭头无法追溯、流程图质量门禁未通过或结果索引未登记时，流程图状态为“未完成”，不得生成正式图、写入论文或作为页数填充。流程图的计算/求解仍与绘图分离：TikZ 源只表达已审计的真实模型结构，不重新计算、猜测或补造结果。

### 16.2 计算与绘图分离

每题保留唯一主入口。计算、验证和绘图分开：

1. 计算脚本从原始输入生成结构化结果，保存到 `求解/问题X/结果/`；
2. 绘图脚本只读取已落盘结果和 Figure Plan，不重新训练、优化、抽样或手工补数字；
3. 新增比较、消融、敏感性、鲁棒性、场景、Monte Carlo 或稳定性分析必须真实运行并保存结果后才能绘图；
4. 固定随机种子、记录运行时间、解释器和视觉编码版本。

每个 Panel 的结果文件、字段、扫描范围、重复次数和统计量在 Figure Plan 中预先声明。绘图脚本不得补算缺失实验；若计划需要而结果文件不存在，返回计算模块真实运行。

### 16.3 结果追溯与命名

正式图保存到 `求解/问题X/图片/`，中间图和字体烟雾测试图不得混入正式目录。文件使用稳定语义化名称；
`求解/结果索引.md` 至少记录图文件、数据源、字段、代码入口、Figure Plan ID、论文标签、生成时间和质量状态。论文只允许引用结果索引中可定位的正式图。

### 16.4 生成与质量门禁

绘图前和绘图失败回退时重新读取绘图规范。正式图必须完成实际渲染和检查：中文字体/负号/希腊字母、图例和刻度重叠、Panel 布局、colorbar、裁切、分辨率、灰度辨识和论文缩放可读性。绘图日志不得静默隐藏字体缺失、布局失败或 colorbar 异常；未通过的图标记为“未完成”，修复后重新生成。

只有以下条件全部满足，图才能进入论文：

- 图支撑一个真实结论，数据和数字可追溯到 `求解/问题X/结果/`；
- Figure Plan、视觉编码表、结果索引、文件名和正文标签一致；
- 图通过绘图规范的字体、语义编码、布局、三维/柱状/饼图限制和质量清单；
- 图文件存在、非空、尺寸/DPI 合理，XeLaTeX 可读取；
- 论文阶段不再重新生成与求解结果不一致的图。

普通 Figure 全部生成后必须运行：

```powershell
python 华为杯_求解规范/tools/audit_visual_plan.py --plan 求解/视觉计划.json --stage render --project-root . --report 求解/视觉计划.render.audit.json
```

该审计核对主结果/验证覆盖、低图量解释、图型族与布局审查、结果文件、绘图脚本、矢量/PNG、统计报告、QA 报告和 `qa_pass` 状态。失败时不得进入论文阶段。

对流程图额外执行 `华为杯_绘图规范.md` 的结构门禁：类型必须匹配真实模型；每个节点和箭头必须能追溯到题面、代码、公式、结果或验证；反馈、分支、验证区和汇总区必须有证据；TikZ/XeLaTeX 必须通过字体、节点重叠、箭头穿字、版心、裁切、灰度和缩放检查。任一项失败时标记“未完成”，不得进入 `求解/问题X/图片/`、结果索引或论文。

### 16.5 论文交接门禁

进入论文阶段前，必须完成全部问题的真实求解、独立验证、正式图生成、图表核验、结果索引和 `audit_visual_plan.py --stage render`。论文规范只负责 `\includegraphics` 路径、图宽、图题、`\label`、正文 `\ref`、PDF 缩放和裁切；绘图视觉风格和图型选择不在论文阶段重新定义。

> 详细规则：`华为杯_求解规范/华为杯_绘图规范.md`。若本摘要与该文件出现细节差异，以绘图规范为准；若与题面硬约束冲突，以题面为准。

## 十七、求解计划.md 编排

`求解/求解计划.md` 是真正指导代码执行的作战文件。

### 17.1 排版

- 使用 Markdown 标题 + 列表
- 不使用复杂 Markdown 表格
- 每个问题独立二级标题
- 一行一个动作
- 文件名、函数名、结果名写清楚

### 17.2 开头：赛题总体判断

必须写：

- 赛题主题
- 问题数量
- 数据规模
- 主要数据类型
- 问题间依赖关系
- 最大技术难点
- 最大硬约束
- 是否需要官方答案附件

### 17.3 每问必须包含 12 个部分

1. **问题目标**
2. **输入**
3. **输出**
4. **题面硬约束**
5. **数据处理**
6. **Baseline**
7. **主模型**
8. **验证方案**
9. **Evidence Matrix（含表达介质）**
10. **Figure / Schematic Plan（含反向数据契约）**
11. **结果 / 图表 / CSV 清单**
12. **支撑材料清单（完整源码、运行验证、自主数据依赖、补充图表）与执行顺序**

### 17.4 模型部分必须具体

不能写：

```text
使用机器学习模型预测
```

必须写成：

```text
Baseline：多元线性回归
主模型：XGBoost Regressor
输入特征：温度、频率、B峰值、B峰峰值、波形统计特征、材料 one-hot
目标：log(损耗)
验证：按材料分层5折；另做材料留一验证检查跨材料泛化
指标：MAE、RMSE、R²、相对误差分位数
```

具体方法根据当前赛题实际调整。

### 17.5 输出清单必须建立数据依赖

例如：

```text
- 磁芯损耗预测结果.csv
  - 来源：主模型预测
  - 用途：论文结果表 + 官方答案表回填

- 模型误差对比.csv
  - 来源：Baseline / 主模型交叉验证
  - 用途：模型选择表

- 预测值与真实值对比图.png
  - 数据源：模型误差对比.csv
  - 绘图函数：绘制预测对比图()
```

- `.txt` 调度序列；
- `.json`；

- 宽 × 高与源图完全一致；
- 二值取值符合题面规定；
- 不应意外保存成带透明通道、调色板或压缩损坏的异常格式；
- 随机抽取若干输出重新读取，核验像素值集合和尺寸。

可生成：

`结果/图像提交核验.csv`

├── Problem1/

```

的明确目录树，必须按原结构生成，不得自行改名。

`提交附件/提交清单.csv`

至少记录：

- 相对路径；
- 文件大小；
- 是否必需；
- 格式核验是否通过。

**压缩格式服从题面。**

1. Codex 先完整生成并验证待打包目录；
2. 不得擅自改成 `.zip`；
3. 输出“待打包目录 + 提交清单”；
4. 明确提示最后一步需由已有 RAR 工具人工打包，除非用户后续提供可调用的 RAR 命令行工具。

### 19.7 支撑材料与 `readme.md` 最终门禁（★ 强制）

`提交附件/最终提交文件/` 保存题面指定的官方输出；`提交附件/支撑材料/` 保存为复核提供的源码、自主数据和补充图表。两者用途不同，但都必须由根目录 `提交附件/readme.md` 列出文件及作用。

```

final 审计至少核对：清单与构建快照未漂移、每问完整源码和主入口存在、运行记录通过、自主数据不是官方原始数据且溯源完整、补充图表存在且有用途、官方输出及其验证存在、无未登记文件、`readme.md` 覆盖全部材料、SHA-256 与当前文件一致。失败不得报告项目完成。

## 二十一、调试与失败处理

### 21.1 防绕圈

同一错误修复最多连续尝试 3 次。

3 次仍失败：

- 停止微调旧代码
- 回到错误根因
- 检查数据/接口/假设
- 必要时重写该模块

### 21.2 模型效果差

按顺序检查：

1. 数据泄漏
2. 标签/单位错误
3. 数据划分不合理
4. 特征是否符合机理
5. baseline 是否正确
6. 指标是否算错
7. 超参数
8. 模型复杂度

不要第一反应就是“换更复杂模型”。

### 21.3 优化不收敛

检查：

- 可行域是否为空
- 初值
- 变量尺度
- 约束冲突
- 目标数量级
- 算法参数
- 数值精度

保存失败案例，不能静默忽略。

## 二十三、华为杯赛题适配检查

开始每届华为杯前，再做一次赛题级适配。

### 如果出现训练集 + 测试集

增加：

- 防泄漏
- 验证集
- test 仅预测
- 官方答案回填

### 如果出现“禁止机器学习”

删除该问题所有 ML 候选方法。

### 如果出现 CPU / 秒级实时性

把：

- 复杂度
- CPU benchmark
- 单步运行时间

提升为核心评价指标。

### 如果出现 MAT / XLS / 多源附件

先写数据读取核验脚本，不直接建模。

### 如果出现 GeoTIFF / NetCDF / GB 级数据

启用：

- 分块
- 空间对齐
- CRS 核验
- 缓存
- 空间验证

### 如果出现星历 / BSP / 高精度时延

启用：

- 高精度时间
- 参考系转换
- 单位核验
- 官方历表 / 可靠库交叉验证

### 如果出现答案 Excel

内部仍保留 CSV 数据仓库，但最终提交必须保持官方 Excel 格式。

### 如果出现图像分割 / 像素级识别

增加：

- 图像尺寸/通道/DPI审计；
- 像素—物理坐标映射；
- 传统图像处理 baseline；
- 分割后处理；
- 输出尺寸 assert；
- 二值像素值核验；
- 图像结果附件逐文件检查。

### 如果出现长时序 / 振动信号 / MAT 文件

增加：

- MAT 变量批量审计；
- 原始文件级分组；
- 先分 train/val/test 再切窗；
- 采样率与转速对齐；
- 时域/频域/包络/时频特征；
- 数据泄漏专项检查。

### 如果出现源域 + 无标签目标域 / 迁移学习

增加：

- 域差异量化；
- 无标签域适配方法；
- 禁止使用目标域真值调参；
- 特征空间可视化；
- 迁移过程或事后可解释性；
- 目标域标签输出与“不代表已验证准确率”的说明。

### 如果出现 DAG / 调度 / 缓存 / 官方评分程序式规则

增加：

- 独立输入解析器；
- 独立可行性验证器；
- 独立官方指标计算器；
- 大规模图复杂度控制；
- 每个官方示例结果汇总；
- 指定 TXT/目录结构自动导出与复核。

### 如果出现多张大图 / 三维重构

增加：

- 分块图像处理；
- 物理坐标统一；
- 二维→三维转换；
- 几何对象匹配；
- 连通概率；
- 不确定性区域；
- 补充测点/钻孔的信息增益排序；
- 三维图与定量结果同步输出。

### 如果出现平面图 + 坐标表 + 矢量 PDF/DWG + 照片的多模态资料

增加：

- 各模态坐标/对象对应关系；
- 优先使用官方 PDF/XLSX 等可读取等价数据；
- 不为 DWG 强制安装 CAD；
- 路径图构建；
- 空间分区/可见性/开合等指标量化；
- 外部资料来源记录；
- 多园林/多对象留出验证。

### 如果出现官方要求 RAR / 特定压缩格式

先自动生成并核验待打包目录。当前三工具链无法生成官方要求格式时，不得用 ZIP 冒充；明确保留最后的人工打包步骤。

## 二十四、最终总原则

华为杯求解不追求“模型名字最复杂”，而追求：

> **题意理解准确 + 硬约束全部满足 + 数学模型有依据 + 算法能运行 + 结果可验证 + 工程上可解释 + 论文素材可追溯 + 官方答案文件零失误。**

最终完成还要求 `audit_supporting_materials.py --stage final` 通过；源码、自主数据、补充图表、官方输出、`readme.md` 与 SHA-256 清单共同形成可提交的支撑材料证据包。

执行时牢记：

**先读题，后建模；先约束，后优化；先基线，后改进；先验证，后结论；先算后画；官方提交格式永远服从题面。**
